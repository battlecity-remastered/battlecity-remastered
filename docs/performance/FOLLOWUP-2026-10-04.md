## City arrival — measured CPU bottleneck and accepted changes

The new `transition=city` diagnostic loads the production `CityLayoutService` conversion of `apps/server-ts/data/cities/Balkh/demo.city`: 47 buildings translated to base (100,150), offscreen to isolate construction work, with stock for all 13 products and four additional moving enemies. Movement, camera follow, existing scenery and projectile replay continue. This is a renderer arrival diagnostic, not a full server/network AI benchmark. The fixture is saved in `src/performance/city-arrival.ts` and source archives.

The original CPU profiles confirmed three separate sources of unnecessary construction work. Each new building immediately rebuilt its shared spatial/material batches; static mixed geometry was merged provisionally and then immediately merged again with final transforms; each laboratory regenerated native `EdgesGeometry` for immutable item meshes. These are CPU stalls, distinct from the shader-permutation stalls addressed in v1.1.7.

Implemented, in measured sequence:

1. Coalesce arrival registrations until the existing batch update before rendering. Each changed batch is resized once, using final world transforms. Default immediate registration remains available. Removal cancels pending batches correctly. Existing eight-tile spatial cells, culling bounds, materials and animation remain unchanged.
2. Construct static merged geometry once from final transforms and visibility. Remove the provisional merge that the first update discarded. Native instancing and multi-draw paths remain unchanged.
3. Cache the exact native 32-degree research-display edges by immutable source geometry, and prepare them during loading. Individual laboratory disposal releases its materials, while shared edges live until the display manager is disposed. There is no global cache or simplified outline. This trades a bounded set of CPU-side outline buffers and loading computation for much less gameplay construction. Renderer-uploaded geometry and texture counts remain unchanged in this diagnostic; CPU cache bytes were not separately measured.

Profiles and intermediate results are retained in `p2-city-*-live/`, including `arrival-analysis.json`. Inclusive stack times overlap and must not be added together:

| Experiment, 360 measured frames | Arrival CPU ms | Worst frame ms | Resize inclusive ms | Edge-generation inclusive ms |
|---|---:|---:|---:|---:|
| Original controls 1 / 2 / 3 | 250.7 / 301.2 / 285.2 | 255.4 / 306.1 / 290.1 | 82.22 / 90.76 / 87.08 | 70.56 / 71.36 / 68.00 |
| Coalesced registration | 239.4 | 244.6 | 43.19 | 84.99 |

| Plus prepared edge cache, finals 1 / 2 / 3 | 134.5 / 125.9 / 126.1 | 139.4 / 130.7 / 132.4 | 13.84 / 12.78 / 14.01 | No gameplay samples |

Research registration drops from roughly 90–93 ms inclusive in controls to 7–10 ms in finals. The final profile still contains model cloning, material construction and one required static merge; this does not eliminate all arrival work.

**Arrival CPU work falls 53.8%, and the worst measured frame falls 48.2%. No steady FPS or p95 improvement is established.** FPS is 0.71% lower; p95 is 1.3 ms worse, p99 0.9 ms better. GPU means and ordinary frame times vary between unchanged controls too. These changes address loading responsiveness; they are not evidence of a new GPU throughput gain or of exhausting all quality-preserving GPU opportunities.

All three earlier short controls/finals are also pooled in [p2-summary.json](p2-summary.json), without excluding the noisier third final: FPS 24.40→24.13, p50 39.3→39.2, p95 52.2→56.6, p99 58.6→68.3, worst 306.1→139.4 ms. Arrival CPU mean 279.03→128.83 ms gives the same 53.8% reduction. This short pool does not support a tail improvement. Keeping both pools prevents selecting only favourable runs.

For the longer pairs, full-trace GC worst durations are 8.07 / 25.03 ms in controls and 23.01 / 12.11 ms in finals. The short third final has a 42.94-ms GC event. Trace GC summaries include warmup and controller result retrieval; they are not phase-mapped to measured RAF intervals, so they do not prove the cause of any measured p99 spike. Allocation-heavy native edge construction is removed from the arrival CPU profiles, but elimination of GC hitches is not claimed.

Each run reports three `blockingProgramLog` events during warmup (simulation 16.7, 216.7 and 1116.7 ms); these are not three newly compiled gameplay shaders. There are no compile/link/log events after the 120-frame warmup, including arrival frame 180. Reserved lighting and existing shader preparation remain intact.

Real loading metadata uses `bench.preparationMs` from the saved native clock. Older `cityPrepareMs` canvas diagnostics use the frozen simulation clock in this harness and must not be interpreted as loading wall time. One short final/control pair reports 1994.5/2062.3 ms, insufficient to claim a startup speedup.

Final scene graph: 7,571 nodes, 6,407 meshes, 550 material instances, 6,461 frozen matrices, 3,670 potential shadow casters and one shadow light. These graph totals are not visible-object or shadow draw-call counts. Scene complexity and approximately 35-ms GPU execution remain substantial. This cycle did not independently time shadow GPU work or isolate fragment/AO cost; yesterday's corresponding profiles and rejected experiments remain authoritative.

Docker reported 1.986 GB total image storage and 1.727 GB reclaimable; apt's download archive was only 48 kB, so another apt cleanup would not solve this.

Database volumes, backups and logs were untouched; server health remained good. Exact commands/deletions/manifests are recorded in `p2-production-storage*.log` and `p2-obsolete-image-manifests.log`.

The remaining usage is about 2.9 GB `/usr`, 1.3 GB Docker, 453 MB Snap files, 278 MB system journals, 258 MB checkout and 244 MB Node versions. The active Docker game log is only 64,241 bytes: no runaway game log is present. `p2-production-disk-breakdown.log` and `p2-production-log-detail.log` preserve the read-only breakdown. Image sizes share layers and cannot be summed as independent disk costs.

Future deployments should retain the running official release and its immediate rollback, verify obsolete releases remain downloadable, and remove only explicitly identified unused official release tags. Preserve the pre-Three rollback and unrelated images unless separately approved. Do not use volume pruning. This small filesystem still has little headroom; old image accumulation explains the immediate problem, but indefinite release/log retention is not sustainable.

## Remaining bottlenecks and next three opportunities

1. Arrival still clones many objects/materials and merges substantial static geometry. Investigate immutable precomputed building buffers/prefabs or reusable cell capacity; preserve shader-local coordinates, eight-tile culling, animation and destruction. Profile full production multi-city arrival/destruction, since this renderer diagnostic does not reproduce server/network stalls or prove the user's full multi-second freeze is gone.
2. GPU execution is still about 35 ms. Investigate exact per-object/tiled finite-light selection or AO geometry batching from new GPU profiles. Reserved slots already avoid compilation; the rejected colour guard adds no demonstrated benefit. Keep all contributing lights, full-resolution AO, shadows, textures and anti-aliasing.
3. Measure multi-city scene-graph/culling and lifecycle soak costs. Consider incremental offscreen hydration only when it cannot delay visible models, collisions, lights or shadows. Trace allocations and map GC events to measured frames before selecting a pooling strategy.

No LOD, resolution, shadow quality, lighting, material simplification or gameplay changes were made. Further same-image GPU improvements are **not proven exhausted**; this cycle has a robust CPU arrival benefit and an honestly inconclusive steady rendering result.
